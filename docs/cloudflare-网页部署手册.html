部署手册 · 网页版

在 Cloudflare 网页控制台部署「今日待办」

全程只用浏览器，不安装任何命令行工具。按顺序做完 ① ~ ⑤ 即可上线， 预计 15 分钟。⑥ 之后的步骤按需选做。

适用项目：todo-today
部署目标：Cloudflare Workers
数据存储：Cloudflare D1
难度：入门
费用：免费额度内

0 · 开始之前

你需要准备

  • 一个 Cloudflare 账号（dash.cloudflare.com 免费注册，无需信用卡）
  • 本项目的全部文件，其中两个文件会在下面被复制粘贴：
    • schema.sql —— 数据库表结构
    • dist/worker.cloudflare-dashboard.js —— 已经打包好的单文件版程序
  • 一个能打开这两个文件的文本编辑器（记事本、VS Code 都行）
为什么是个「单文件」？ Cloudflare 网页版的代码编辑器只能编辑一个文件，也没有上传静态网页 （HTML / CSS / JS）的入口。所以项目已经预先打包成 worker.cloudflare-dashboard.js： 它把后端代码和整个前端页面都装进了一个文件，Worker 会自己把网页返回给浏览器。 功能与命令行部署完全一致，只是少了一层目录拆分。

两种部署方式怎么选

方案 A · 网页控制台（本手册）方案 B · Git 自动构建
需要命令行不需要不需要，但需要一个 GitHub 仓库
代码更新手动重新粘贴一次代码推送代码后自动部署
适合先跑起来、个人使用、不想碰命令行长期维护、多人协作

方案 B 见文末附录 B。两条路用的是同一份源码，可以先用方案 A 上线，日后再迁到方案 B。

① 创建数据库（D1）

1新建 D1 数据库

目标：得到一个空的 SQL 数据库，用来存账号和待办。

  1. 登录 dash.cloudflare.com。
  2. 在左侧导航进入 Workers & Pages›D1 SQL 数据库 （英文界面是 Storage & Databases › D1 SQL Database）。
  3. 点 Create database / 创建数据库。
  4. 名称填 todo-today，点创建。
创建后请留在当前页面 下一步要在这个数据库的 Console（控制台） 里执行建表语句。

2执行建表语句

目标：把 users / sessions / todos / settings / notifications / notify_log 六张表建出来。

  1. 用文本编辑器打开项目里的 schema.sql，全选并复制全文。
  2. 回到 D1 数据库页面，切换到 Console / 控制台 标签页。
  3. 把 SQL 粘贴到输入框，点 Execute / 执行。
  4. 看到执行成功的提示后，切到 Tables / 表 标签确认， 应该能看到 6 张表：users、sessions、todos、settings、notifications、notify_log。
这段 SQL 可以重复执行 全部语句都带 IF NOT EXISTS，重复执行不会报错、也不会清空已有数据。 唯一的例外是给 todos 补 due_date 列的 ALTER TABLE： 如果之前建过库、列已经存在，重复执行会提示 duplicate column name，直接忽略即可。
务必确认执行的是「远程」数据库 Console 页面上会标注当前目标（Remote / 远程 还是 Local / 本地实例）， 请确保是远程。如果建成了本地表，线上注册时依然会报 no such table: users。等后面把 Worker 部署上线后，可以访问 https://你的地址/api/health?check=1 复核，看到 "schema":{"ok":true,...} 才算真的建好了。

② 创建 Worker 并粘贴代码

3创建一个空 Worker

目标：先拿到一个占位的 Worker，再去编辑它的代码。

  1. 左侧导航进入 Workers & Pages。
  2. 点 Create application / 创建应用程序。
  3. 选择 Create Worker / 创建 Worker（页面上通常写作 Start with Hello World!，或从模板列表里选 Hello World）。
  4. 名称填 todo-today，点 Deploy / 部署。
  5. 几秒后会得到一个地址，形如 https://todo-today.你的子域.workers.dev。先不用打开它， 此时它还是个 Hello World。

4把单文件代码粘进去

目标：让 Worker 变成「今日待办」。

  1. 在 Worker 详情页点 Edit code / 编辑代码，打开在线编辑器。
  2. 在编辑器里按 Ctrl+A 全选，Delete 清空默认的示例代码。
  3. 用文本编辑器打开 dist/worker.cloudflare-dashboard.js， Ctrl+A 全选、Ctrl+C 复制。
  4. 回到在线编辑器，Ctrl+V 粘贴。
  5. 点右上角 Save and Deploy / 保存并部署。
  6. 打开 https://todo-today.你的子域.workers.dev，应该能看到登录界面。
必须粘贴完整，一行都不能少 文件约 3600 行 / 240 KB，其中大量长字符串是内联进去的网页文件。 如果粘贴后页面显示空白或样式全丢，多半是复制不完整——重新全选复制一次即可。 粘贴后建议在编辑器里按 Ctrl+End 跳到文件末尾， 确认最后一行是 }; 且不是半截内容。
现在登录会报错，这是正常的 此时数据库还没绑定，接口会返回「未绑定 D1 数据库」。做完下一步就好了。

③ 绑定数据库

5把 D1 绑定到 Worker

目标：让 Worker 里的 env.DB 指向刚才创建的数据库。

  1. 进入这个 Worker 的 Settings / 设置 页面。
  2. 找到 Bindings / 绑定，点 Add binding / 添加绑定。
  3. 类型选 D1 database / D1 数据库。
  4. 变量名称填 DB（必须完全一致，区分大小写）
    数据库选 todo-today
  5. 保存。Cloudflare 会自动重新部署，大约 10 秒完成。
绑定名写错是最常见的失败原因 必须是 DB。写成 db、MY_DB、D1 都不行， 页面会能打开但一操作就报错。

验证：浏览器打开 https://todo-today.你的子域.workers.dev/api/health， 看到 {"ok":true,...,"db":true,...} 就说明绑定成功了。

④ 设置环境变量

6添加变量（可选但建议）

目标：配置站点名称，并决定是否开放注册。

  1. Worker 的 Settings / 设置 页面，找到 Variables and Secrets / 变量和机密。
  2. 点 Add / 添加，按下面的表填，类型都选 Text / 文本。
  3. 保存并等待自动重新部署。
变量名值作用
APP_NAME今日待办健康检查接口里显示的站点名
ALLOW_REGISTRATIONtrue / false设为 false 即关闭注册
只想自己用？ 先保持 ALLOW_REGISTRATION=true 注册好你自己的账号，再把它改成 false。 之后任何人都无法再注册。

⑤ 上线检查

7走一遍完整流程

目标：确认所有功能都正常。

  • 访问 /api/health?check=1 → 返回 "schema":{"ok":true,"missing":[]}（最先验这个， 能一次性排掉「没建表」「绑定名写错」两类问题）
  • 打开站点，能看到「今日待办」的登录界面，并且底部是「登录 / 注册」两个标签页
  • 切到「注册」，用任意用户名 + 6 位以上密码创建账号 → 成功进入主界面
  • 在输入框输入一件事，回车 → 列表出现这条待办，底部计数变成「1 项待完成」
  • 输入框只敲空格再回车 → 提示「任务内容不能为空」，没有新增任何任务
  • 点任务前面的圆圈 → 变成勾选状态并沉到列表底部，计数减 1
  • 点任务右侧的垃圾桶图标 → 该条消失，计数同步变化
  • 点右上角头像打开设置抽屉 → 能看到「当前账号」是你的用户名
  • 用手机浏览器打开同一地址 → 布局正常、按钮好点
  • 刷新页面 → 刚才的待办还在（说明数据库写入成功）
  • 退出登录再重新登录 → 数据仍在

⑤b · 可选：到期提醒

任务可以设一个「到期日」，到点前自动把提醒推到 Bark / Telegram / 飞书 / 企业微信 / 邮件等 12 种渠道。这个功能依赖 Cron Triggers，网页粘贴部署（方案 A）必须先做这一步：

8添加 Cron 触发器（网页部署必须）

目标：让 Worker 每 5 分钟自己跑一轮，到点能自动推送与备份。

  1. Worker 详情页 → Settings / 设置 › Triggers / 触发事件 › Cron Triggers。
  2. 点 Add Cron Trigger / 添加触发器，表达式填 */5 * * * *，保存。
  3. 打开站点 → 右上角头像 → 到期提醒，面板底部应显示 「定时任务运行正常（每 5 分钟检查一次）」。
备份与提醒共用这一个 Cron 每 5 分钟一轮：既驱动「定时备份」，也驱动「到期提醒」，不用建两个。 Git 自动构建（方案 B）已在 wrangler.jsonc 里配好，无需手动添加。

9配置提醒渠道

目标：选好推送渠道并填上密钥，先用「发送测试」验证。

  1. 打开站点 → 右上角头像 → 到期提醒。
  2. 打开「启用到期提醒」，在推送渠道里点选要用的渠道 （可多选，点选后下方会展开该渠道的参数表单）。
  3. 按表单提示填写（例如 Bark 填 Device Key、Telegram 填 Bot Token 与 chat id）； 密钥留空表示不修改，已保存过的不会回显。
  4. 按需调整：提前几天提醒（0–365 天，0 = 只在当天）、 每天几点后推送（免打扰）、 是否到期前每天提醒、是否提醒已过期任务。
  5. 先点 发送测试（不用先保存也能测），收到消息后再点 保存配置。
  6. 给任务设到期日：卡片右侧的「+ 到期」或新增任务输入框旁的「到期日」按钮， 选好日期即可；到点前会自动推送。
没收到？按这个顺序查 ① 面板底部有没有「定时任务运行正常」（没有就是上面的 Cron 没配）； ② 任务有没有到期日（只有带「N 天后到期」徽标的才会被提醒）； ③ 是不是还没到「每天几点后推送」的时间——点立即检查可绕过免打扰立刻验证； ④ 点「发送测试」看具体报错，后端会把上游返回的错误原因带回来。

⑥ 可选：配置云备份

主线功能到上一步就完成了。下面是可选的「再存一份到别处」，三种方式选一种即可。 无论选哪种，都是在站点的设置抽屉 → 云备份里填。

ACloudflare R2（原生绑定，无需密钥）

目标：把备份写进 R2 存储桶。

  1. 左侧导航进入 R2 对象存储›创建存储桶。
  2. 存储桶名称填 todo-backups，创建。
  3. 回到 Worker 的 Settings / 设置 › Bindings / 绑定， 点 Add binding / 添加绑定。
  4. 类型选 R2 bucket / R2 存储桶。
  5. 变量名称填 BACKUPS（必须完全一致）
    R2 存储桶选 todo-backups
  6. 保存并等待重新部署。
  7. 打开站点 → 右上角头像 → 云备份：
    • 备份方式选 Cloudflare R2（原生绑定）
    • 打开「启用云备份」，按需打开「变更后自动备份」
    • 点 保存配置，再点 测试连接，最后点 立即备份
自动备份有节流 开启「变更后自动备份」后，每 60 秒最多上传一次，避免频繁改动把请求配额打满。

BS3 兼容对象存储（含 R2 / AWS / MinIO / 阿里云 OSS 等）

目标：用密钥直连任意 S3 兼容服务。

在站点的设置抽屉 → 云备份里选「S3 兼容对象存储」，按下表填写：

字段怎么填
Endpoint 服务地址例如 R2：https://<账户ID>.r2.cloudflarestorage.com
MinIO：http://你的域名:9000
RegionR2 填 auto；AWS 填真实区域如 us-east-1
Bucket你的桶名，例如 todo-backups
Access Key ID / Secret在对应平台的 API 令牌页面生成
路径前缀 / 文件名可留空，默认写 todo-today.backup.json
Path-StyleMinIO 等自建服务一般勾上；AWS 与 R2 不勾

填完依次点 保存配置 → 测试连接 → 立即备份。

密钥也可以放在 Worker 里 如果不想把 Secret Key 存在页面上，可以留空，改为在 Worker 的 Variables and Secrets 里添加一个加密类型的 BACKUP_S3_SECRET_KEY。页面留空时会自动回落到它。

CWebDAV（坚果云 / Nextcloud / 群晖等）

目标：备份到自己的网盘目录。

在设置抽屉 → 云备份里选「WebDAV」，填写：

字段怎么填
WebDAV 目录地址坚果云：https://dav.jianguoyun.com/dav/我的坚果云/todo
Nextcloud：https://cloud.示例.com/remote.php/dav/files/<用户名>/todo
用户名你的登录邮箱 / 用户名
密码坚果云需在「账户信息 → 安全选项」里生成应用密码
目录必须已经存在 WebDAV 一般不会自动创建目录，请先在网盘里手动建好那个文件夹。 密码同样可以留空，改用 Worker 机密 BACKUP_WEBDAV_PASSWORD。

⑦ 可选：绑定自己的域名

＋用自定义域名访问

  1. Worker 的 Settings / 设置 页面，找到 Domains & Routes / 域和路由。
  2. 点 Add / 添加 › Custom domain / 自定义域。
  3. 输入你想用的域名，例如 todo.你的域名.com，确认。

域名的 DNS 需要托管在 Cloudflare（在 Cloudflare 里添加站点并改好 NS 即可）， 证书由 Cloudflare 自动签发，无需额外操作。

⑧ 以后怎么更新代码

如果你改动了 src/ 或 public/ 里的源码，需要重新生成单文件并替换：

  1. 在有 Node.js 的电脑上，进入项目目录执行：
    npm run build:dashboard
  2. 重新打开 dist/worker.cloudflare-dashboard.js 复制全文。
  3. Cloudflare 控制台 → 该 Worker → Edit code / 编辑代码。
  4. Ctrl+A 全选清空，粘贴新代码，点 Save and Deploy。
只是想改网页样式或文案？ 同样要走这个流程——前端文件是被打包进 Worker 的，不是独立上传的。

常见问题

注册时提示 D1_ERROR: no such table: users: SQLITE_ERROR

这是最常见的一个问题：数据库本身建好了、也绑上了，但库里还是空的 —— 也就是第 ② 步的建表没做，或者做在了本地实例上。

回到 D1 → 点进你的 todo-today 数据库 → 切到 Console（控制台） 标签页 → 把项目里的 schema.sql 全文粘进输入框 → 点 Execute（执行）。

执行完刷新页面重新注册即可。想确认是否成功，访问 https://你的地址/api/health?check=1，看到下面这样就说明表齐了：

{"ok":true,"db":true,"schema":{"ok":true,"tables":["users","sessions","todos","settings","notifications","notify_log"],"missing":[]}}
注意别执行到本地实例上

Database 的 Console 里不要选成 Local / 本地实例， 要选远程的那个数据库，否则线上依然是空表。页面上会标注当前的执行目标是本地还是远程。

Git 自动部署时构建失败：D1 binding 'DB' references database '…' which was not found [code: 10181]

这是方案 B（Git 自动构建）的问题：仓库里 wrangler.jsonc 的 database_id 填的不是你自己账号里那个 D1 数据库的 ID （这个 UUID 每个账号都不一样，不能从教程或别人的配置里照抄）。

正确的 ID 这样找：

  1. 打开 Cloudflare 控制台左侧 存储和数据库 (Storage & Databases) › D1 SQL Database
  2. 点进你实际在用的 todo-today 数据库（拿不准就选之前线上已经在用的那个）
  3. 在概览页右侧找到 Database ID，点复制按钮

然后到 GitHub 仓库里编辑 wrangler.jsonc，把 database_id 换成它并提交， Workers Builds 会自动重新构建部署。

别绑到一个新的空库上

如果你账号里有多个 D1，务必选线站在用的那个。 绑到新建的空库会「部署成功但数据全没了」，还得对新库补执行一遍 schema.sql 建表。

更稳的验证方法：Workers & Pages → 点进 Worker › Settings › Bindings（绑定），看 DB 这条 D1 绑定指向的数据库名， 点进去复制它的 Database ID，保证两边是同一个库。

打开站点是空白页，或样式全部丢失

99% 是代码粘贴不完整。重新打开 dist/worker.cloudflare-dashboard.js， 全选复制后，在在线编辑器里 Ctrl+A 全选覆盖 —— 不要手动滚动着补。

页面能打开，但一注册就提示「未绑定 D1 数据库」

说明第 ③ 步的绑定没做或名称不对。检查 Settings › Bindings 里的变量名是否精确等于 DB（大写，无空格）。

注意和上一条区别开：报 未绑定 D1 数据库 是没连上库； 报 no such table 是连上了但没建表。

设置里开了「定时备份」，但一直提示「还没收到定时任务的心跳」

定时备份靠 Cron Triggers（定时触发器）驱动，代码部署后还要加一条触发规则：

  1. 打开 Workers & Pages → 点进你的 Worker（todo-today）
  2. Settings › Triggers（触发事件）
  3. 在 Cron Triggers 里点 Add Cron Trigger
  4. 填入 */5 * * * *（意思是每 5 分钟唤醒一次），保存

加好之后回到应用的设置页，等最多 5 分钟，「定时任务运行正常（上次检查 x 分钟前）」就说明生效了。 备份周期本身（每 15 分钟 / 每小时 / 每天……）在应用内设置里选，不需要改这条 Cron。

只想用「变更后自动备份」的话 不加这条 Cron 也完全没关系——那个功能由你的操作触发，不依赖定时器。
怎么快速确认后端是否正常？

访问 https://你的地址/api/health。正常会返回类似：

{"ok":true,"app":"今日待办","db":true,"r2":false,"registration":true}

db:false 表示 D1 没绑上；r2:false 只是说明没配 R2 备份，不影响使用。

加上 ?check=1 则会真的连一次数据库，并把缺失的数据表列出来 —— 部署完自查时建议用这个：/api/health?check=1。

提示兼容性日期相关的问题

在 Worker 的 Settings › Runtime / 运行时 里把 Compatibility date / 兼容性日期 设为 2025-05-01 或更晚，保存后重新部署。

云备份报「未绑定 R2 存储桶」

要么去第 ⑥-A 步添加 R2 绑定（变量名必须是 BACKUPS）， 要么把备份方式改成 S3 或 WebDAV。三种方式任选其一，不必都配。

「测试连接」失败怎么办？
  • S3：检查 Endpoint 是否多了结尾斜杠、Bucket 名是否正确、Region 对 R2 必须是 auto；自建 MinIO 记得勾 Path-Style。
  • WebDAV：检查目录地址是否已存在、密码是否用了「应用密码」而不是登录密码。
  • 跨域的报错信息会直接显示在设置抽屉下方的状态行里，按提示排查即可。
我能不能用命令行部署？

可以，Web 控制台部署和命令行部署用的是同一份源码，互不影响。 命令行的步骤见项目根目录 README.md 的「部署到 Cloudflare」一节， 那种方式还支持配置静态资源目录，属于另一种部署形态。

开了到期提醒但一直没收到？

按顺序排查：

  1. Cron 没配：设置面板底部显示「尚未检测到定时任务心跳」就是这个问题， 到 Worker 的 Settings › Triggers › Cron Triggers 添加 */5 * * * *。
  2. 任务没设到期日：只有带「N 天后到期」徽标的任务才会被提醒， 任务所属日期（出现在哪一天）不参与提醒。
  3. 没到免打扰时间：「每天几点后推送」设了 09:00 就要等 9 点后； 点立即检查可绕过立刻验证。
  4. 已经推过一次：每个「任务 + 到期日 + 渠道」只推一次， 想重新收到就把任务的到期日改一下。
  5. 渠道参数错：点「发送测试」，报错里会带上游返回的具体原因。

附录 B · 方案 B：用 Git 自动构建

适合需要长期维护的场景。代价是需要一个 GitHub 账号和仓库。

  1. 把整个项目（不含 node_modules 和 dist）推送到 GitHub 仓库。
  2. 先在网页控制台按第 ① 步创建 D1 数据库，复制它的 Database ID。
  3. 把该 ID 填进仓库里的 wrangler.jsonc 的 database_id 字段并提交。
  4. 网页控制台进入 Workers & Pages›创建应用程序， 选 Import a repository / 导入存储库，授权并选中该仓库。
  5. 构建配置保持默认（Cloudflare 会自动识别 wrangler.jsonc 并执行 wrangler deploy），点部署。
  6. 之后每次 git push 都会自动构建并上线，无需再手工粘贴代码。
这种方式还多一个好处 它支持在 wrangler.jsonc 里声明 assets 静态资源目录， 网页资源由 Cloudflare 的 CDN 直接托管，比打包进 Worker 更快。 用这种方式时，第 ② 步的「粘贴单文件代码」可以整步跳过。

方案 A 与方案 B 的功能完全一致

两条路走的是同一份源码，只是静态资源的分发方式不同：

对比项方案 A · 网页粘贴单文件方案 B · Git 自动构建
后端代码 同一个 src/index.js 入口
前端文件 public/ 打包成 base64 内联在单文件里 public/ 由 assets 绑定直接托管
账号与数据隔离 完全一致
待办功能 / 日期选择 / 加载速度 完全一致

因为后端是同一个文件，「不同账号各自管理自己的待办」这件事在两条路径上都成立—— 它由 Worker 里的会话校验和 user_id 过滤保证，与前端怎么分发无关。 前端只负责切换账号时清干净本地缓存，这部分代码两条路径也共用。

方案 B 唯一要额外注意的是：别漏传 public/ 目录

方案 B 不靠内联，而是直接读取仓库里 public/ 目录下的文件。 如果 .gitignore 里误写了 public/，或者提交时漏掉了这几个文件， 部署出来的网站会是空白页或者旧版本。

确认方法：在 GitHub 仓库页面能看到 public/app.js、public/index.html、 public/style.css 这三个文件。改完前端后，记得 git add public/ 一并提交。

切换方案时不用重新建库 两个方案连的是同一个 D1 数据库，账号和待办数据都在库里。 无论从 A 换到 B 还是反过来，已有账号和待办都原样保留，直接登录即可。
